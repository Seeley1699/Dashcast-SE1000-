# 投屏卡死修复说明（v2.8.2，2026-10-30）

> 现象：**点开始投屏，仪表上去一帧就停住，两条传输链路（BGRA+LZ4 / H.264）表现完全一样。**
> 结论：这是 v2.8.1 引入的回归，已在 v2.8.2 修复并在真机（e04-p171）验证通过。

---

## 一、故障机理

### 1.1 双缓冲是怎么工作的

`dashcastd` 用 wl_shm 建了 N 个 buffer 轮流提交给 Weston：

```
acquire_buffer() → 拷贝像素 → wl_surface_attach + commit → flush
                        ↑
              只有收到 wl_buffer.release 事件，
              busy 才会清 0，这块 buffer 才能再被取用
```

`release` 事件是**合成器通过 wayland socket 回传的**，必须真的从 socket 读出来才算收到。

### 1.2 v2.8.1 的错误改法

v2.8.1 为修"多线程抢 wl_display socket 导致的 cleanup 卡死"，把主循环的：

```c
while (running) { wl_display_dispatch(display); }     // 阻塞，会读 socket
```

换成了：

```c
while (running) {
    wl_display_dispatch_pending(display);             // ✗ 只清内部队列，从不读 socket
    usleep(2000);
}
```

`wl_display_dispatch_pending()` 的语义是"把**已经进到队列里**的事件派发出去"，它**不会**调用 `read`。于是：

1. 第 1、2 帧顺利提交（此时 2 个 buffer 都空闲）
2. 两个 buffer 都 `busy=1`
3. `release` 事件躺在 socket 里，没人读 → `busy` 永远是 1
4. 第 3 帧起 `acquire_buffer()` 恒返回 NULL → 帧被**静默丢弃**
5. 画面永久停在第 2 帧

两条链路共用 `commit_frame()`，所以 BGRA 和 H.264 同时卡死 —— 这正是"两个链路都一样"的原因。

### 1.3 为什么之前没测出来

v2.8.1 的验收只发了 **1 帧**。单帧永远只需要 1 个 buffer，看不出 release 有没有回来。

> **教训：验证双缓冲/多缓冲链路，至少连续发 N > buffer 数量的帧。**
> 现在的回归工具 `dc_e2e --ok 200` 就是为此写的，200 帧 = 50 个 buffer 周转周期。

## 二、修复内容

### 2.1 用官方三段式泵事件（`wl_pump_locked`）

```c
static void wl_pump_locked(int timeout_ms)
{
    while (wl_display_prepare_read(display) != 0) {
        if (wl_display_dispatch_pending(display) < 0) return;
    }
    wl_display_flush(display);

    struct pollfd pfd = { wl_display_get_fd(display), POLLIN, 0 };
    int pr = poll(&pfd, 1, timeout_ms);
    if (pr > 0 && (pfd.revents & POLLIN)) {
        if (wl_display_read_events(display) < 0) return;   // 真的读 socket
    } else {
        wl_display_cancel_read(display);
    }
    wl_display_dispatch_pending(display);
}
```

这是 libwayland 官方推荐的多线程用法：`prepare_read` 占位 → `poll` 等 → `read_events` 读 → `dispatch_pending` 派发。**所有调用都在 `wl_mutex` 内**，所以任何时刻只有一个线程碰 socket，既不会并发死锁，也不会漏读 release。

### 2.2 buffer 数 2 → 4

双缓冲在 30fps 持续推流下不够：合成器 release 稍慢就会出现周期性"无 buffer 可用"。实测双缓冲 200 帧丢 61 帧（30%）。

| buffer 数 | 200 帧实测 |
|---|---|
| 2 | 丢 61 帧（30%） |
| **4** | **丢 0 帧** ✅ |

### 2.3 等待预算 24ms

`acquire_buffer_locked()` 每轮 pump 3ms、最多 8 轮 ≈ 24ms。30fps 单帧预算 33ms，留 8~9ms 给 4MB memcpy（约 1~2ms）+ attach/commit/flush，不会把下一帧挤掉。

### 2.4 主循环不再参与 wayland 事件

改成纯 `usleep(5000)` 维持进程存活。事件驱动完全交给持锁的 `commit_frame()` / `blank_frame()`。

### 2.5 顺手修：`CpManager.pushLocal` 假成功

```java
// 修前：只要远端 md5sum 有输出就算成功
return md5.length() > 0;

// 修后：本地算 md5，远端比对，不一致返回 false
String localMd5 = md5Hex(bin);
...
boolean ok = remoteMd5.equalsIgnoreCase(localMd5);
```

**为什么重要**：dropbear 的 exec 命令长度上限很小。分片 6000 字符时偶发被截断，远端 `base64 -d` 产出残缺文件，但 `md5sum` 照样有输出 → 报 `PUSH_OK`，实际 CP 上还是旧二进制。

排查时这个坑极其隐蔽：日志显示"部署完成"，但 CP 上跑的是老版本，改了代码等于没改。现在分片降到 4000，并且 md5 严格比对。

## 三、新增排查指标（出问题时先看这两个数）

`dashcastd` 现在每 30 帧打一行、每个会话结束打一行汇总：

```
提交 30 帧 / 1.35s = 22.2 fps（累计丢 0）
会话结束，图层已还原（本会话提交 200 帧 / 丢 0 帧），等待下一个连接
```

**判读方法：**

| 现象 | 含义 |
|---|---|
| `提交` 计数持续增长 | 画面在动，链路正常 |
| `提交` 计数不涨、`丢帧` 不涨 | AP 侧没发帧（画面静止 / 目标 App 没内容） |
| `丢帧` 持续增长 | CP 侧 buffer 周转跟不上（合成器卡顿或 buffer 不够） |
| `丢帧` 涨到接近 `提交` 数 | 双缓冲/单缓冲问题复发 |

配合 AP 侧 `dcapd2.log` 的 `STAT fps/capture/tiles/kbps` 一起看，能一步分清是"AP 没发"还是"CP 没上屏"。

## 四、真机验收数据（e04-p171）

### 4.1 BGRA+LZ4 档

```

提交 30 帧 / 28.75s = 1.0 fps（累计丢 0）        ← 影视仓首页静止，正常
（滑动制造动态）AP: tiles=199 kbps=2170          ← 2.1 MB/s
                CP: 提交帧率上升，累计丢 0
```

### 4.2 H.264 档

```
AP:  STAT fps=27~29 capture=29 tiles=0 kbps=7~11
CP:  h264rx: 帧=2128 NAL=2270 喂=2270 | rv1=2128   ← 解码成功 2128，零错误
     提交 30 帧 / 1.03s = 29.1 fps（累计丢 0）
```

```
连续 200 帧        → 提交 200 / 丢 0
60 帧 × 3 轮会话   → 各丢 0，每轮图层都干净还原
畸形越界帧         → "图块越界: (1800,500 64x64) 画布 1920x532" 拦截，进程存活
```

## 五、给后续维护者的提醒

1. **任何改动 `commit_frame` / `acquire_buffer` / wayland 事件循环的提交，都必须用 `dc_e2e --ok 200` 回归**。只发 1 帧测不出 buffer 周转问题。
2. **不要在多个线程里自由调用 `wl_*` 函数**。所有 wl 调用必须持 `wl_mutex`，且读 socket 只走 `wl_pump_locked`。
3. **改 buffer 数量后要重新量丢帧**。`NUM_BUFFERS` 在 `dashcastd.c` 顶部，改动会影响 shm pool 大小（4 × 4085760 ≈ 16MB，CP 内存 1755MB，余地充足）。
4. **推二进制后必须校验 md5**。App 侧现在会自动比对并打日志；手工推的话自己 `md5sum` 对一遍，别信"命令没报错"。
