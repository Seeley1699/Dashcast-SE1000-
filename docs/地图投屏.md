# 地图投屏（MapCast）

把车机自带地图（`com.geely.map`）的**地图画面**直接铺到仪表盘，不走「搬 App 进虚拟屏」那条路。

---

## 一、为什么不能纯 APK 实现

| 需求 | Dashcast 自己做 | 地图进程做 |
|---|---|---|
| 建 1920×532 的 VirtualDisplay | ✗ 缺 `CAPTURE_VIDEO_OUTPUT`（signature 级） | ✓ 有 |
| 让地图引擎把画面渲染到指定 Surface | ✗ 引擎单例不在我们进程 | ✓ 原生有 |

实测两条硬限制：

```
Dashcast 进程调 createVirtualDisplay(1920x532)
  → SecurityException: Requires CAPTURE_VIDEO_OUTPUT ...

Dashcast 进程 PathClassLoader 加载 Map.apk 后
  new HUDControl()                  ✓ 能实例化
  HUDControl.initSurfaceView(...)   ✗ mMapService = null（引擎没在跑）
  com.autonavi.gbl.map.MapService   ✗ UnsatisfiedLinkError（JNI 未注册）
```

**结论：必须注入 `com.geely.map` 进程，让地图自己画。**

## 二、完整链路

```
用户点「地图投屏」
    │
    ▼
MapCastService（App 内，worker 线程）
    │
    ├─① 解压 assets/hudcast-inject.bin（gzip 56MB ELF）→ /data/local/tmp/hudcast-inject
    ├─② 解压 assets/mapcast.js → /data/local/tmp/mapcast.js
    ├─③ cp 部署 dashcastd（已有 CpManager）
    │
    ├─④ LongLivedShell.spawnDcapd2()
    │     setsid dcapd2 1920 532 0 0 1920 532 1920 532 198.18.34.2 8444 30 0
    │
    └─⑤ LongLivedShell.spawnInjector()
          setsid hudcast-inject -p <地图pid> -s mapcast.js
    │
    ▼
地图进程内（mapcast.js）
    │
    ├─ VirtualDisplay("DashcastMap", 1920, 532, 160, surface, 0x3)
    │     flags = PUBLIC(0x1) | PRESENTATION(0x2)   ← 0x3 是关键
    ├─ basemap.MapView(displayContext)
    │     addView(lp{ type = 2038  TYPE_APPLICATION_OVERLAY, 1920x532 })
    ├─ HUDControl hc = new HUDControl()
    │     hc.surfaceViewID = 5                      ← SURFACE_VIEW_ID_HUD
    │     hc.initSurfaceView(mv, true, 1920, 532)   ← 引擎在这里注册 slot 5
    │     hc.setCarLogoVisible / setLayerVisible / setDynamicLevel / renderResume
    │
    └─ 每帧：PixelCopy.request(Surface, bmp, ...)
              bmp.copyPixelsToBuffer(bb)            ← 无 ColorMatrix，字节序直接对
              VDF1(0x56444631) + w/h/stride + BGRA → 127.0.0.1:8450
    │
    ▼
dcapd2（抓 VD 帧源）
    ├─ 收到 DCBG(44 43 42 47 小端) → svc 从 SCREEN 切到 VD
    └─ LZ4 图块 → TCP 8444
    │
    ▼
CP (198.18.34.2) dashcastd
    └─ wl_shm ARGB → ivi layer 99（1920x532 全屏）→ Weston 合成 → 仪表盘
```

## 三、这条链路踩过的坑（都是实测结论）

### 1. VirtualDisplay 的 flags 必须是 0x3

```
0x1 (PUBLIC)              → Presentation.show() 抛 InvalidDisplayException
0x3 (PUBLIC|PRESENTATION) → show() 成功
```

### 2. 注册 MapView 的唯一入口是 `HUDControl.initSurfaceView`

自己调 `MapService.createMapView(MapViewParam)`：
- 参数不全 → 返回 null
- 参数填满 → **FATAL 死锁**（futex_wait_queue_me）

`initSurfaceView` 内部会：
```
getMapView(5)  从 null → 有效对象
getDevice(4)   从 null → 有效对象
mapViewMap     {1: 主屏} → {1: 主屏, 5: HUD槽位}
```

### 3. PixelCopy 必须用 `Surface` 重载

```java
PixelCopy.request(SurfaceView, bmp, ...)  // 含叠加在上面的 View → 搜索框被抓进来
PixelCopy.request(Surface,     bmp, ...)  // 只抓 Surface 内容  ✓
```

### 4. `copyPixelsToBuffer` 出来的就是 dcapd2 要的字节序

```
同一帧 A/B 对比（4 个采样点全部一致）：
  getPixels  : R=24 G=164 B=248 A=255
  copyPixBuf : [0]=24 [1]=164 [2]=248 [3]=255
```
**不要加 ColorMatrix 做 R/B 互换** —— 加了车标由蓝变橙。

### 5. `AdbShell.exec` 起不了长活进程

```
AdbShell.runCommand 收到 A_CLSE 就返回，
exec() 随即 closeQuietly() / 复用 socket；
adbd 在这条 shell 流关闭时把该流创建的子进程组一起回收。
```
试过 6 种写法都失败（`( & )` → `setsid --fork` → `setsid` → `nohup setsid` → `sh -c '...' &`）。

**解法 = `LongLivedShell`**：开独立 socket，`OPEN` 后把 socket 保存在静态字段**不关**。
App 持有它就等于给子进程续命；`stop()` 时 `releaseAll()` 关 socket，进程组随之回收。

`LongLivedShell` 自己的两个坑：
- `A_CNXN` 的 arg0/arg1 必须填 `A_VERSION`/`A_MAXDATA`，**填 0 会让 adbd 对后续 OPEN 完全不响应**
- 等 `A_OKAY` 超时**不能关 socket** —— 命令已发出去了，关了等于自己杀掉刚起的进程

### 6. 地图进程重启后注入会失效

`MapCastService` 有 watchdog，每 5 秒查一次地图 pid，变了就重注入。

### 7. `dcapd2` 的遮罩配置必须清

`/data/local/tmp/dcapd2.layer` 若残留（上次投屏的旧截取区），会把新画面裁成一条缝：
```
图层遮罩生效: shape=1 矩形=799,56 1x416     ← w=1
```
`startDcapd2()` 每次都先 `rm -f`。

### 8. ★ 地图有两个同包进程，必须注入 `u11` 那个

**这是最难查的一个**（2026-11-08，表现是"UI 卡在正在启动，后台其实全绿"）。

```
$ ps -A -o pid,user,args | grep com.geely.map
  766  u11_a128  com.geely.map    ← 真正的 UI / 渲染进程，要注这个
  8788 u0_a128   com.geely.map    ← 辅助进程（无窗口、无 Activity）
```

原来用 `pidof com.geely.map | 取最后一个 pid`，注进了 `u0` 那个。后果：

```
VirtualDisplay 建起来了（displayId=23，flags=0x3，都正常）
addView 也 OK
initSurfaceView 也 OK（isInitOk=true）
    ↓
但 PixelCopy 全部失败：code=3  ERROR_SOURCE_INVALID
    ↓
地图侧 frames 恒为 0
dcapd2 侧 STAT capture=0（收到 DCBG 切了 VD，但一帧都收不到）
```

**为什么难查**：前三步日志全是 OK，只有 PixelCopy 静默失败。

**修法**：
```java
// 不要用 pidof（输出顺序没有任何保证）
String r = AdbShell.exec(
    "ps -A -o pid,user,args 2>/dev/null | grep 'com.geely.map' | grep -v grep", 6000);
// 只挑 user 以 u11 开头的那行
```

watchdog 也必须用同一套规则 —— 否则 `u0` 那个进程会让它一直误判
"进程变了"，反复重注入。

### 9. 日志 `>>` 追加时 `rm -f` 清不掉

用来等首帧的判据是"日志里出现某行"，但日志清不干净就会**命中上一轮的旧记录**：

```
① rm -f dcapd2.log          → 旧进程持有 fd，只是 unlink，
                              内容继续写进已删的 inode；新进程重建同名文件
                              → 两份日志交错，实测累积到 1.4 万行
② pkill; sleep 1; : > log   → 还是不行！被杀进程回收 fd 时会把缓冲区
                              flush 回去，内容又变回旧的
③ ✅ pkill → Thread.sleep(2000) 等真的死透 → 单独一条命令 : > log
```

**手动复现 ②**：
```sh
echo A >> /data/local/tmp/dcapd2.log        # 25 行
pkill -9 -f dcapd2; sleep 1; : > .../dcapd2.log
wc -l .../dcapd2.log                        # 仍然是 25 行
```

**必须分成两次 `AdbShell.exec`，中间 `Thread.sleep`**，不能一条命令串做完。

### 10. 首帧判据的四种错法（都试过）

`waitFirstFrame()` 要判断"地图的画有没有真的送到 dcapd2"，先后用错四次：

| 版本 | 判据 | 结果 | 原因 |
|---|---|---|---|
| ① | `tail -20 \| grep 出真画面` | 假阴性 | 那行在启动后第 30 行就打了，等 bootSequence 结束时尾部全是 STAT |
| ② | 全文 `grep -c 出真画面` | 假阳性 | 日志没清干净，命中上一轮的记录，67ms 就报"成功" |
| ③ | `totalKB > 0` | 假阳性 | dcapd2 启动会先推一帧**主屏**（`src=SCREEN`, `totalKB=492`），41ms 命中 |
| ④ | `src=VD && tiles>0` | 假阴性 | **静止画面没有图块差量，`tiles=0` 是常态**；`tiles=48` 只闪一下，采样落在 0 那秒就判失败（实测 `fps=7 tiles=48 kbps=154` 已推流成功却报"未出帧"） |
| **⑤ ✅** | `VD 帧N: ... 空屏=0` | 正确 | 由**帧源每收到一帧**就打，不受"画面有没有变化"影响 |

**窗口也要给够**：从 `injectMap` 返回（进程都起来了）到 dcapd2 真的收到首帧，
实测要 **13-20 秒**：
```
injector 起来(3s) → 建 VirtualDisplay → addView → initSurfaceView 注册 slot 5
→ 引擎开始画 → PixelCopy 出帧 → VDF1 到 dcapd2 → 日志出现 "VD 帧"
```
原来给 12 秒，会误报"未出帧"。现在 25 秒。

### 11. UI 状态要跟着后台进度走

`MapCastService` 的 callback 原来只更新了 `mapCastState` 那行小字，
顶部大号 `status` 一直停在"正在启动地图投屏…" —— **用户看到的就是"卡了"**，
其实后台 11 秒就跑完了。

```java
MapCastService.get().start(this, msg -> mainHandler.post(() -> {
    if (mapCastState != null) mapCastState.setText("地图投屏：" + msg);
    setStatus("状态：" + msg);                    // ← 必须补这句
    if (msg.contains("失败") || msg.contains("未启动")) { /* 恢复按钮 */ }
}));
```

## 四、协议速查

| 常量 | 值（小端字节） | 用途 |
|---|---|---|
| `CMD_BG` / DCBG | `44 43 42 47` | 切 dcapd2 到 VD 模式 |
| `VDFRAME_MAGIC` / VDF1 | `31 46 44 56` | 帧包头 |
| `CMD_VCROP` / DCVP | — | 源裁剪框（16 字节） |
| `CMD_SRC` / DCSR | — | 主屏截取区热更新 |

帧包 = `magic(4) + w(4) + h(4) + stride_px(4) + BGRA(stride_px*h*4)`，全小端。

## 五、实测性能

```
地图侧（PixelCopy + 拷贝） : 11.0-11.2 fps, 2ms/帧, 0 错误
dcapd2 → CP              : capture=11/秒, src=VD, totalKB 递增
CP dashcastd             : 提交 568 帧 / 丢 0 帧
bootSequence             : 11 秒（进程全部就绪）
注入 → 首帧              : 13-20 秒（injector 起来 → 建 VD → 注册 slot 5
                            → 引擎开画 → PixelCopy 出帧 → VDF1 到 dcapd2）
点按钮 → UI 显示"运行中"  : 约 25 秒（含上面那段等待）
```

> **帧率不是 30fps 的原因**：`dcapd2` 只在画面**有变化**时才编码发图块。
> 地图静止 → `tiles=0`，但帧源那边一直在收帧。所以 `capture=11` 是帧源
> 收到的帧数，`tiles` 是这一秒发出去的差量图块数 —— 两个数字含义不同，
> 看 `tiles=0` 不要以为链路断了。

## 六、前置：注入器二进制要自己生成

`src/ap/app/src/main/assets/hudcast-inject.bin`（24MB）**不进版本库**，需要从原车
「银河世界.apk」的 `assets/runtime/hudcast-inject.xz` 提取：

```powershell
powershell -ExecutionPolicy Bypass -File tools\fetch-injector.ps1 `
    -SourceApk 'F:\Desktop\车机\银河世界.apk'
```

脚本会输出 MD5，正常值 `a65d370d24668525136882adee64326b`。

**必须用 7-Zip 解压**：那个 xz 是 `ARM64(BCJ) → LZMA2` 滤镜链，Python 的 `lzma`
不支持 ARM64 BCJ，解出来只有 25MB 且运行时段错误。

## 八、截图验证

```powershell
powershell -ExecutionPolicy Bypass -File 'F:\Desktop\dashboard-shot.ps1'
```

正常输出应包含：

```
cp: SID=9001-layer99      ← 抓的是投屏层
cp: SZ=4085814
```

**如果没有 `SID=9001-layer99`，说明投屏没开或 layer 99 不存在**，此时脚本会退回
抓 layer 10（原厂仪表）。

> 那个 CP 侧 bash 脚本（`dashboard-shot-cp.sh`）**必须是纯 ASCII**。
> 之前在里面写了中文回显，UTF-8 到 CP 后按 GBK 解码，`?` 吃掉闭合引号，
> `echo "SID=..."` 语法崩坏，SID 为空走 fallback —— 表现为「截图永远是原厂画面，
> 但文件大小、传输、SZ 全都正常」，极难查。
