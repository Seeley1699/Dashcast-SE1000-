# 给 dashcast 加第二档传输通道（H.264）—— 可行性与方案

> 结论先说：**能加，也能做成可切换的。但这台 CP 没有硬解码器，H.264 只能软解。**
> 所以真正的问题不是"能不能写"，而是"软解吃不吃得下 30fps"。这一条必须先量。

---

## 一、先看硬件底牌（2026-10-29 实机探测结果）

在 CP（198.18.34.2）上跑出来的事实：

```
/dev 下的视频节点：
  video0..3 + gdc / out / raw / meta
  /sys/class/video4linux/*/name 全部是：
      siengine-gdc
      isp_v4l2-vid-cap-m2m / -raw / -out / -meta
```

这些是 **ISP 采集**通道（摄像头那条路），**不是解码器**。
没有 `/dev/vpu*`、`/dev/mpp*`、没有 V4L2 stateful decoder，
`/usr/lib` 里也没有 `libavcodec` / `libopenh264` / 任何 VPU 用户态库。

CPU / 内存：`nproc = 2`，内存 1755 MB（空闲 849 MB）。

**判定：**
- "CP 已 DPU 加速"这句话在我们这台车上**不成立**。DPU 是显示合成单元
  （做图层混合/缩放），不是视频解码器。文字里把它当解码加速写，是营销口径。
- H.264 在 CP 上只能**软件解码**，占用的是那 2 个核里的一个半。

---

## 二、两档通道到底差在哪（决定架构）

| | BGRA+LZ4（现有） | H.264（要新增） |
|---|---|---|
| 数据形态 | 64×64 图块差量 | 整帧视频码流 |
| 传送 | TCP，可靠 | UDP + RTP，容忍丢包 |
| AP 侧代价 | CPU 读回 + LZ4 | MediaCodec 硬编，CPU ≈ 0 |
| CP 侧代价 | LZ4 解压 + memcpy | **软解 H.264**（新开销） |
| alpha | ✅ 逐像素真透明 | ❌ 无，4:2:0 |
| 静态画面 | 几乎不占带宽 | 仍需周期 IDR |
| 全屏动态 | 12–15 MB/s，增量失效 | 1–2 MB/s，这是它的主场 |

**产品层面的硬约束：** 一旦切到 H.264，形状遮罩、羽化、圆角、梯形变换
全部失效 —— 它们都建立在 alpha 上。透明区域会变成黑块盖住原厂仪表。
所以这档只能用于**整屏矩形铺满**的内容，不能用于卡片叠加。

---

## 三、架构（改动落在哪）

```
                    ┌──────────── AP ────────────┐        ┌──────── CP ────────┐
 目标窗口/虚拟屏 ──▶ 采集 ──▶ [编码选择]           │        │                    │
                             ├─ BGRA: 分块+LZ4 ───┼─TCP──▶ │ 现有: 贴图 → shm   │
                             └─ H.264: MediaCodec ┼─UDP──▶ │ 新增: 解码 → 贴图  │
                                                     RTP          （openh264）  │
```

**握手要改一处**：现有 8444 的握手包里加 1 字节 `codec`
（1 = BGRA+LZ4，2 = H.264）。CP 收到后决定是走图块流还是起 UDP 接收线程。
**其余全部复用**：同一块 shm 画布、同一个 ivi 图层 99、同一套 render order 逻辑。
切换档位不需要重连、不需要重启 dashcastd。

**AP 侧**（dcapd2.c，新增约 500 行）
- `MediaCodec` 走 C++（NDK AMediaCodec），`createInputSurface()` 直喂，
  省掉一次 CPU 读回（BGRA 那条必须读回，这条不用）
- 码率 CBR 3–6 Mbps 可调，GOP 1 s，`baseline + no B-frames`（低延迟）
- RTP 打包：RFC 6184，单 NAL + FU-A 分片；时间戳 90 kHz
- 关键帧请求：CP 收不到就发 RTCP PLI（或者简化成自己的 2 字节回执）

**CP 侧**（dashcastd.c，新增约 600 行 + 一个解码库）
- UDP 收包 → 去 RTP 头 → 组帧（按 marker 位判帧尾）
- 解码：**openh264**（BSD，纯解码约 1 MB，有 NEON），zig 交叉编 aarch64 静态链进去
- 输出 I420 → 转 BGRA 写进现有 shm 画布 → `wl_surface_commit`
- 丢包策略：解不出来就保持上一帧，等下一个 IDR（1 秒内恢复）

**选择入口**（约 100 行）
- App 里加一个「传输编码」单选（就是你截图那个位置）
- 存 prefs → 拉起 dcapd2 时作为参数传入 → 握手带给 CP
- 切换时：停当前流 → 重连 → 新档生效，仪表最多黑 1 帧

## 四、真正的不确定性：软解够不够快

960×528 @30fps = 0.5 MP/s×30。openh264 在 ARM 上通常能到 100+ fps@720p，
按面积折算这台机器大概率够，但**两个核还要同时跑 Weston 合成和我们的渲染**，
没有任何余量可以浪费。

所以第一步不是写通道，是**写一个基准**：

```
bench_dec.c  —— 读一段预编码的 960×528 H.264（录一次就行），
                用 openh264 解 300 帧，打印：
                  · 平均解码耗时 / 帧
                  · 能跑多少 fps
                  · 进程 CPU 占用
                  · 与 Weston 同时跑时的掉帧
```

判定线：
- ≥ 40 fps 且 CPU < 60%/核 → 可以上，实际跑 30fps 有余量
- 25–40 fps → 能上但只能跑 24fps，且要降分辨率到 720×396
- < 25 fps → 这档在这台车上没有意义，如实告诉他，不硬上

## 五、工作量与顺序

| 阶段 | 内容 | 预估 |
|---|---|---|
| 0 | 软解基准（openh264 交叉编译 + 实测 fps/CPU） | 半天 |
| 1 | 协议握手加 codec 字段 + CP 起 UDP 解码线程 + 屏幕出画（先不接 AP） | 1 天 |
| 2 | AP 侧 MediaCodec 编码 + RTP 打包 + 联调出画 | 1 天 |
| 3 | App 里加单选 + 热切换 + 断流恢复 | 半天 |
| 4 | 实测两档带宽/CPU/延迟对比，出表 | 半天 |

**总改动约 1200 行**，两个二进制都要换，CP 侧多链一个静态解码库（体积 +1 MB）。

## 六、要拍板的一件事

H.264 档 **没有 alpha**。这不是实现问题，是 4:2:0 格式决定的。

所以这档的定位只能是：
- ✅ 整屏播放视频 / 全屏地图 / 摄像头画面
- ❌ 仪表上叠半透明卡片、形状遮罩、羽化

如果卡片叠加是主场景，那 H.264 永远只能是"临时切一下看视频"的备用档，
默认仍应该是 BGRA+LZ4。这个定位需要产品上认下来，否则做完了会发现用不上。

## 七、实测结果（2026-10-29 22:40，真机 CP）

**方法**：`cp/bench_dec.cpp` 用 openh264 2.2.0（Ubuntu arm64 构建）在 CP 上解
`nature_704x576_25Hz_1500kbits.h264` 的前 41 个 slice（14 帧，每帧 3 slice，含 B 帧），
每轮重置解码器，跑 10 轮取平均。程序只读文件、只在内存解码，不碰任何显示设备。

**实测（2 次复测一致）：**

```
帧数        : 131 / 79
wall        : 3.23 s / 1.97 s
cpu         : 2.54 s / 1.51 s
fps         : 40.6 / 40.0
ms/frame    : 24.6 / 25.0   (wall)
cpu/frame   : 19.4 / 19.1   (单核 CPU 时间)
cpu load    : 79% / 77%     of one core
```

**换算**：704×576 = 0.4055 MP → **47.3 ms CPU / MP / 帧**（含 B 帧、High profile，
我们的编码用 baseline 无 B，会更快一些，这是偏保守的上界）。

按这个系数推算（只算解码，不含 YUV→BGRA 转换与 blit，那部分约 +4~6 ms/帧）：

| 编码尺寸 | MP | 解码 CPU/帧 | 跑 30fps 占单核 | 判定 |
|---|---|---|---|---|
| 1280×704 | 0.90 | 42.6 ms | 128% | 不可能 |
| 960×528 | 0.51 | 24.0 ms | 72%（+转换 ≈ 85%） | 刚好够，没余量 |
| 800×440 | 0.35 | 16.7 ms | 50%（+转换 ≈ 62%） | 有余量 |
| 704×396 | 0.28 | 13.2 ms | 39%（+转换 ≈ 50%） | 舒服 |

CP 是 2 核。960×528@30 大约吃掉 **整机 43% 的 CPU**，留 1.1 个核给 Weston 和系统 ——
能跑，但一旦有别的负载就会掉帧。800×440 是更稳的默认值。

**结论：可行，但定位是"够用的备选档"，不是主力通道。** 主力仍是 BGRA+LZ4：
静态几乎零带宽、有 alpha、像素完美。H.264 只在整屏播视频时切过去。

**清理确认**（测完）：`/run/dcbench` 已删、`/tmp/dcbench` 已删、dashcastd(pid 3097)
未受影响、render order 仍为 `[10]`、`weston.ini` md5 与测前一致
（`e826ad28b25bfe36f86cfd4f404e365f`）。

## 八、960×528 真机上屏实测（2026-10-29 22:53）

**做法**：把一帧真实界面用 `screenrecord --size 960x528 --bit-rate 3000000` 录下来
（硬件编码，就是将来走的那条编码器），转成 Annex-B，推到 CP，用
`ldemo --demo demo60.h264 35 960 528` 解码后直接提交到 ivi 图层 99，
**端到端跑 35 秒**，然后自动清理。

**结果：**

```
帧=1017  耗时=35.02s  fps=29.0  CPU/帧=14.13ms  单核=41%  循环=16
图层已清理（第 1 次验证通过），render order=[10]
EXIT=0
```

**这条比估算好很多**：纯解码基准推算 960×528 要 24 ms/帧（含 B 帧、High profile 的
最坏情况），而实际端到端（解码 + YUV→ARGB + memcpy 进 shm + commit）只要 **14.1 ms/帧**、
**41% 单核**。原因是真实编码流是 baseline 类（无 B 帧），解码器轻松很多。

**结论修正：960×528@30 完全跑得动**，占单核 41%（整机约 21%），
加 UDP 收包也只是零头。之前按最坏情况推的"刚好够、没余量"是过于保守。
800×440 仍然更省，但 960×528 不再是"没余量"的选项。

**安全确认**：`/run/dc2` 已删；dashcastd(3097) 未动；render order 回到 `[10]`；
weston.ini md5 仍为 `e826ad28b25bfe36f86cfd4f404e365f`。

## 九、H.264 档正式实现（2026-10-30 01:10，端到端跑通）

### 链路

```
AP: SurfaceFlinger 抓屏 → 合成 1920×532 画布
    → MediaCodec 硬件编码（video/avc, baseline, 2.5Mbps, 30fps）
    → 4 字节大端长度 + 一个 NAL，写进已建好的那条 TCP 控制连接
CP: 读长度前缀 NAL → 补 Annex-B 起始码 → openh264 软解
    → YUV→BGRA → shm → 提交 ivi 图层 99（960×266，合成器拉伸到 1920×532）
```

### 三个关键决策（都是实测逼出来的，不是拍脑袋）

1. **不走 UDP/RTP，走 TCP。** 这台车机的 AP↔CP 链路会把每个 UDP 包送两份
   （AP `sendto` 零失败发 67 包/s，CP 收到 138 包/s，重复率 53%）。
   重复包把 FU-A 分片拼两遍，码流直接废掉 —— 一帧都解不出来。
   TCP 保证不重不丢不乱序，点对点 USB 网上也没有队头阻塞的实际代价。
   代价：RTP/FU-A 那一整套（约 200 行）全删了，换成 `[u32be len][NAL]` 的简单流。

2. **喂 openh264 前要补 4 字节起始码。** 线上格式是裸 NAL（长度已经定界），
   而 `VIDEO_BITSTREAM_DEFAULT` 只认 Annex-B。不补的话每个 NAL 都返回 0，一帧不出。

3. **色度平面按 NV21 写，不是 NV12。** 编码器报 `cf=0x15`
   （`OMX_COLOR_FormatYUV420SemiPlanar`），名义是 NV12，但这颗 SoC 实际按 NV21 吃。
   按 NV12 写会整体 R/B 互换：青绿主色 `#37C1A5` 变成橄榄色。
   现在按 cf 自动定（19→I420，21/39/flexible→NV21），可用 `DC_UV_SWAP` 覆盖。
   验证方法：整幅均值 R/B 关系要和 AP 屏幕一致（AP 是 B>R，修复前是 R>B，修复后 B>R）。

### 实测（真机，App 点按钮切档，抖音 → 仪表）

```
帧率        : 28.6 ~ 28.8 fps（5 秒窗口，CP 解码侧计数）
CPU/帧      : 6.50 ms   （/proc/<pid>/stat 的 utime+stime 差分）
占单核      : 19%        整机（2 核）约 10%
带宽        : 静态约 53 KB/s，视频约 300~360 KB/s
解码错误    : 0
```

之前按最坏情况推的 24ms/帧、单核 85% 是**严重高估**。原因有两个：
一是真实编码流是 baseline 无 B 帧；二是仪表那块面板是 1920×532（超宽，3.6:1），
半分辨率只有 **960×266 = 0.26 MP**，比估算时用的 960×528（0.51 MP）还小一半。

### 尺寸说明（跟最初的估算对不上，说明一下）

最初按 16:9 估的是 960×528。实际面板 1920×532，所以半分辨率是 **960×266**。
CPU 只用了 19% 单核，**余量很大**。想要更清晰可以加档：

| 编码尺寸 | MP | 估算 CPU/帧 | 30fps 占单核 | 判定 |
|---|---|---|---|---|
| 960×266（当前） | 0.26 | 6.5 ms（实测） | 19% | 很省，视频够用 |
| 1440×400 | 0.58 | ~14.5 ms | ~44% | 更锐，仍有余量 |
| 1920×532（不缩放） | 1.02 | ~26 ms | ~78% | 太贴顶，Weston 会被挤 |

改档只动一行：`dcapd2.c` 里 `g_enc_w/g_enc_h` 的除数。

### 代码落点

| 文件 | 作用 |
|---|---|
| `ap-native/h264enc.c` | MediaCodec 编码 + BGRA→YUV + TCP 长度前缀发送 |
| `ap-native/dcapd2.c` | argv[12] 收档位；握手 flags 带编码尺寸；H.264 档推流分支 |
| `cp/h264rx.c` | TCP 收 NAL、补起始码、解码、YUV→BGRA、提交；每 5 秒打统计 |
| `cp/h264shim.cpp` | openh264 的 C++ 虚表包成 4 个 C 函数 |
| `cp/dashcastd.c` | 握手解析 flags；codec==2 走 h264_rx_run；清理复用 cleanup_layer |
| `src/dashcast_proto.h` | `DASHCAST_CODEC_H264=2`；flags 位域编码尺寸宏 |
| App | 「视频档」切换按钮；档位存 SharedPreferences，重启 App 记得住 |
| `cp/build-dashcastd.sh` | openh264 静态链入，二进制自包含（只依赖 CP 原有的 wayland + libc） |

### 已知取舍

- **没有 alpha。** 卡片遮罩/羽化/圆角在 H.264 档全部失效，这是格式决定的。
  所以默认仍是 BGRA+LZ4，H.264 靠按钮手动切。
- **不支持中途切回 BGRA 再切回来的热切换**（切档会重启 dcapd2，有一瞬黑屏）。
- CP 复用 TCP 控制连接传码流，所以 H.264 档下 TCP 上不再有图块流量，
  dcapd2 每秒探一次控制通道，CP 重启后能自动重连。
