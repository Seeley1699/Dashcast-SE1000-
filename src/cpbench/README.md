# cpbench —— 编码模式压测的安全契约

测的是「BGRA+LZ4」和「H.264 RTP」两种模式的真实代价：带宽、AP/CP 的 CPU、丢帧。
前提只有一个：**无论怎么搞砸，仪表都不能留在坏状态，断电重启必须回到原厂。**

---

## 一、为什么这个测试不可能把仪表搞砖

"变砖"意味着改了**持久化**的东西（分区、固件、开机配置）。这个测试从头到尾不写持久分区：

| 我们碰的东西 | 在哪 | 重启后 |
|---|---|---|
| `dashcastd` 二进制 | `/run/dashcastd` | **消失**（`/run` 是 tmpfs，内存盘） |
| 日志 | `/run/dashcastd.log` | 消失 |
| 图层 99 | ivi-shell 的**运行时**层表 | 消失（weston 重新初始化） |
| render order | ivi-shell 运行时属性 | 回到 weston 启动默认值 |
| `weston.ini` | `/etc/xdg/weston/` | **我们一个字节都不写** |

`preflight` 会实测 `/run` 是不是 tmpfs、有没有开机自启项 —— 任何一条不满足直接中止，不进入测试。

真正的风险不是"砖"，是**测试期间仪表短暂无显示**（图层摘掉、原厂画面还没重绘的那一两秒）。
所以：**车必须停稳再测**，不要在路上跑。

---

## 二、四层保护，从外到内

**第 1 层：CP 上的死手开关（最重要）**

`arm` 会在 CP 上起一个脱离 SSH 会话的独立脚本，每 5 秒看一眼心跳文件：

```
心跳 45 秒没更新  →  摘掉 render order 里的 99 + 杀掉 dashcastd + 记日志
```

宿主机崩了、adb 掉线了、我这边断网了 —— 只要车还通着电，45 秒内仪表自己就回去了。
这个脚本在 `/run/cpbench/`，重启一样消失。

**第 2 层：显式还原（`restore`，幂等）**

停守护 → 杀进程 → 重设 render order → 清 `/run` 残留 → 停 AP 侧 dcapd2。
中途任何一步失败都可以重复跑，不会越跑越糟。

**第 3 层：持久分区指纹自证**

`preflight` 存下 `weston.ini` 的 md5，`verify` 再算一次比对。
两个值一致 = 整个过程没碰过持久配置，有据可查，不是"我觉得没碰"。

**第 4 层：断电重启**

即使前面全失效，`/run` 是内存盘，CP 一重启我们的东西就不存在了，仪表回到车厂默认。

---

## 三、出事了怎么办

| 现象 | 动作 |
|---|---|
| 仪表黑屏 / 只有底图 | 等 45 秒（看门狗），没恢复就跑 `./bench.sh restore` |
| 仪表画面卡住不动 | 同上 |
| `restore` 也报错、连不上 CP | 断电重启。这是最后一招，也一定有效 |
| 车机 ADB 掉线 | 不用管，看门狗会自己收拾；重连后 `./bench.sh verify` |

---

## 四、跑法

```bash
cd dashcast/tools/cpbench
./bench.sh preflight          # 只检查，不动任何东西
./bench.sh arm                # 装看门狗
./bench.sh measure 30         # 测当前界面上的模式，30 秒
#   → 在车机上把编码切到另一档
./bench.sh measure 30         # 再测一次
./bench.sh restore
./bench.sh verify
```

一条龙：`./bench.sh all 30`（测一档就还原）。

## 五、测什么

- **CP 接收带宽**：`/sys/class/net/*/statistics/rx_bytes` 两点差分 —— 这是带宽的物理真相，
  不信任何应用自己报的数字。
- **CP 整机 CPU**：`/proc/stat` 的 idle 差分 —— 回答"会不会把仪表那颗 CPU 吃满"。
- **AP 侧**：`dcapd2` 的 fps / 上行，从它自己的 STAT 行读。
- **主观项**：文字边缘是否发虚、透明区域是否变黑块、拖动时是否跟手。

H.264 那档要特别看两件事：
1. 有没有 alpha —— 卡片遮罩、羽化、圆角会不会变成黑块；
2. CP 是不是真硬解 —— 如果 CP CPU 在 30fps 下飙到 80%+，那"DPU 加速"就是文案。
